## What the helper read but did not turn into a requirement

- Cookies. If a cookie exists, MDN says to use `Secure`, `HttpOnly` where script does not need it, a `__Host-` or `__Secure-` name prefix, and `SameSite=Lax` or `Strict` (https://developer.mozilla.org/en-US/docs/Web/Security/Practical_implementation_guides/Cookies). A static contact page should set no cookie. The builder could add a check "no `Set-Cookie` header or `document.cookie` write unless the owner asked", and then apply these attributes to any cookie that remains. Grade if added: convention.
- `Server` and `X-Powered-By` headers. OWASP says to remove or neutralise them, and adds that attackers have other ways to fingerprint a server. A static host usually controls them. Grade if added: expert opinion.
- `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy`, `Cross-Origin-Embedder-Policy`. OWASP and web.dev recommend them. OWASP warns that COEP blocks cross-origin resources that are not set up for it. They add little to a page with no cross-origin resources. Left out.
- `X-XSS-Protection`, `Expect-CT`, `Public-Key-Pins`. OWASP says do not use these (set `X-XSS-Protection: 0` or leave it out). Left out. A check that none of them is sent is possible.
- Trusted Types (`require-trusted-types-for 'script'`). Recommended by web.dev and OWASP "where supported". Heavy for a one-file page. Left out.
- Reporting endpoints (`report-to`, `report-uri`). They need a server that receives reports. Left out for a static page.

## What a program cannot check

- Whether the form's receiving endpoint (a form service, mail script, or database) validates input, stores data safely, limits repeat submissions, or keeps data private. The page shows only the address it posts to.
- Whether a header that a response shows is set at the host for every path. nginx drops inherited `add_header` lines inside a nested `location` block, and Apache `Header set` and `Header always set` use different tables (OWASP HTTP Headers sheet). A program can request several paths, including an error page, but cannot see the host's configuration.
- Whether the host's certificate renews, who holds the private key, and which TLS versions and ciphers the host allows. A program can read what a handshake negotiates but not why.
- Whether a content security policy blocks something the owner needs. Only a person using the real page in a real browser sees that.
- Whether the owner's choice to name a form endpoint, a map, or a booking widget is wise. Those are third-party trust decisions.
- Spam, bot abuse, and email-header injection in the endpoint that sends the form to the owner. None of the pages read covers them.
- Any claim that the whole page resists attack. No check here establishes that, and the Prescription and the Honest receipt must not say it.

## Conflicts or doubts

1. HSTS values differ. OWASP's header sheet recommends `max-age=63072000; includeSubDomains; preload`. web.dev (2021) recommends `max-age=31536000` alone. MDN gives both as examples. The candidate S13 takes one year, the figure web.dev recommends and the minimum that MDN names for preload (OWASP's sheets use two years; neither states that one year is acceptable) and leaves `includeSubDomains` and `preload` to a person, because `preload` is hard to undo and the owner may not control every subdomain. This is a choice by the helper, not a rule from a source.
2. `X-Frame-Options` is called obsolete by OWASP's CSP and header sheets, yet MDN's clickjacking page and web.dev both say to send it too. S15 keeps both. The OWASP clickjacking sheet also marks `ALLOW-FROM` as dead; S15 does not use it.
3. Header versus `<meta>`. OWASP and web.dev both allow CSP in a `<meta>` tag but say framing protection, sandbox, and reports do not work there. OWASP calls the header "the preferred way". S5 therefore uses `<meta>` because a one-file page may have no header control, and S15 must be a header. A `<meta>` policy cannot be tested in report-only mode (web.dev strict-CSP page).
4. Hash-based policy is brittle. OWASP warns that changing even whitespace inside a script changes the hash. A page with a script must have its hash recalculated at every edit. The simplest policy for a page with no script is `script-src 'none'`. The helper judges that the Mockup's "no script" rule makes this the common case; no source says so.
5. Inline styles are not settled. MDN says nonces and hashes also work on `<style>` elements, and that `'unsafe-inline'` "defeats much of the purpose of having a CSP". None of the pages read states how strict a `style-src` must be on a static page, or whether inline `style=""` attributes are an acceptable risk. The builder needs an owner decision on `style-src` (hash of each `<style>`, a separate same-origin stylesheet, or `'unsafe-inline'` for styles only). S5 does not set a rule for it.
6. `rel="noopener"` is redundant. MDN says `target="_blank"` already implies it in modern browsers. S7 stays because it is cheap and makes the intent visible. `noreferrer` is added by the helper to stop the Referer header leaving, which MDN's `noopener` page says `noopener` alone does not do.
7. Referrer-Policy is already `strict-origin-when-cross-origin` by default in browsers (MDN). OWASP still says to set it explicitly. S8 follows OWASP.
8. Permissions-Policy is marked "Experimental" and "Limited availability" by MDN. S16 is graded expert opinion for that reason.
9. S9 and S10 stretch password pages to contact forms. The MDN Passwords page is written for sign-in flows. The helper applied its form-markup and HTTPS rules to a contact form. A small-business page should have no password field; that is a scope decision for the owner and not a source rule.
10. Autocomplete row and accessibility. The MDN autocomplete page links the tokens to WCAG 1.3.5. The project rule says never to claim accessibility of output, and the accessibility Floor is a separate, overridable Floor. S10 is therefore worded as form-markup correctness only.
11. Dated sources. web.dev security-headers was last updated 2021-05-18 and mixed content 2019-09-07; the web.dev CSP article carries 2012-06-15 and is dropped as a basis. The OWASP HSTS sheet says "as of September 2019". The OWASP pages show no date at all; the helper read the live pages on 2026-11-16 and they mention items from 2024 to 2025 (Top 10:2025, nginx 1.29.3), so they are current in content, but the page version cannot be pinned. A reviewer should record the fetch date as the version.
12. Static hosts. The helper did not read any host's documentation. It is not known which simple static hosts allow response headers, or how (some offer a headers file; this was not verified). If a host allows none, S12 to S16 become "owner must accept this gap" lines in the Prescription, not failed checks.
13. OWASP's own XSS sheet states that CSP "should not be your primary defense mechanism". S5 to S6 are an extra layer that sits on S3 and S4, not a replacement for them.
