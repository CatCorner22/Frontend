## What a program cannot check

1. INP (P3). Only real users decide when to interact, and which interactions they choose. A scripted run measures only the interactions the script performs. web.dev: lab tools without a user "cannot measure INP, as there is no user input" (https://web.dev/articles/vitals). A person or field data must judge INP.
2. The 75th percentile. Every published limit (P1 to P3) applies to the 75th percentile of real page loads, split by mobile and desktop. One lab load is one sample, on one device, one network and one place (https://web.dev/articles/lab-and-field-data-differences). The Fit check can say "this run measured 2.1 s"; it cannot say the page meets the limit for most visitors. Suggestion (mine, not from a source): run several loads and report all values, not one.
3. What changes the lab number. The lab browser loads with a cold cache, one viewport, no personalised content, no A/B test, no bfcache, and the viewer's installed fonts may differ. So the lab LCP element can differ from the field LCP element. The viewport size, device scale factor, CPU and network settings of the Fit check change P1, P2, P5 and P10, so the Prescription must record them with every result. I did not read any source on Playwright throttling settings.
4. Post-load layout shifts. Lab CLS covers the load and whatever the script does. A shift caused by lazy-loaded content when a visitor scrolls, or by a banner that appears later, appears only if the script scrolls and waits. Scripted clicks also set `hadRecentInput` and hide the shifts they cause, as real clicks do.
5. Whether an animation is "in response to a tap or key press" (P13), and whether a layout shift is "expected" by the person, need a person's judgement.
6. Whether a late image really looks like the largest or most important element to a visitor. LCP picks the largest element, and web.dev notes (https://web.dev/articles/lcp) that the most important element on a page can be a different one.
7. Third-party content. The Prescription forbids remote scripts and fonts, so most of this does not arise for the owner's pages, but cross-origin Resource Timing sizes read as 0 without `Timing-Allow-Origin` (https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming), so P9 and P14 would undercount any cross-origin file.
8. Whether the real host serves compressed files, sets cache headers, or uses HTTP/2 or a CDN. The local test server may differ; I did not read a source with limits on these.
9. Anything about how a visitor feels the page loads (a splash screen, a spinner, a late reveal by script). The measures say when pixels appear, not whether the page feels finished.

## Conflicts or doubts

D1. Different numbers between pages: none found for the three Core Web Vitals limits. web.dev gives the same good limits (LCP 2.5 s, INP 200 ms, CLS 0.1) on vitals, lcp, cls, inp and defining thresholds, and no page gives a different number. The poor limits (LCP 4 s, INP 500 ms, CLS 0.25) are written out on defining-core-web-vitals-thresholds; INP 500 ms is also on /articles/inp and CLS 0.25 also on /articles/cls. The vitals and lcp pages state no poor limit. The INP chart that shows the thresholds is a figure I could not see; the text of https://web.dev/articles/inp states the numbers, so I relied on that.
D2. Wording of "passing". https://web.dev/articles/vitals says tools "should consider a page passing" at the 75th percentile for all three. This project forbids the word "passes" as a claim about output, so the Fit check must say "measured at or under the published limit in this run", not "passes".
D3. Dates that do not match content. The footer of "Preload critical assets" says last updated 2018-11-05, but its text discusses INP and the Core Web Vitals, which did not exist in 2018. So the footer date is probably stale and the page was edited later. The "Responsive images" page (2014) says only pixel-density `srcset` is "well-supported today", which is out of date: MDN documents `w` descriptors and `sizes` as normal. The font page (2022) and the lazy-loading analysis (2022) are older than the 2025 pages. Treat page footers as uncertain dates; none was checked against another source.
D4. The 170 KB budget (P14) comes from a 2018 page, was derived for a slow phone on 3G, and sits beside a Time to Interactive goal. That page names TTI as a metric to track, while the 2024 and 2025 pages use INP and name TBT as the lab proxy. I could not verify from an allowed host whether TTI is still recommended. I recommend the builder not use the 5 s TTI number, and treat the 170 KB number as expert opinion only.
D5. `font-display` numbers. web.dev gives block and swap periods in a table (`optional`: 100 ms block, no swap; `fallback`: 100 ms block, 3 s swap; Chromium and Firefox block up to 3 s by default). MDN gives no numbers and says only "extremely small" and "short". They do not conflict, but only web.dev has numbers. Also, the web.dev font page's `@font-face` code example contains syntax mistakes (a comma after the `src` value, `font-display` inside the `src` declaration, no semicolon after `font-family`); do not copy that snippet into a Prescription.
D6. Self-hosting fonts. Project rule says no remote fonts. web.dev's font page says self-hosting is not clearly faster in practice, and gives conditions (CDN, HTTP/2). The Floor can require same-origin fonts (P9) for the project's reasons, but this record gives no performance reason for it.
D7. "Preload". web.dev says to preload sparingly; the same site's LCP advice says a CSS-only background image needs a preload. Both hold: P6 asks for a preload only when the LCP image is not in the HTML, and P11 caps preloads. The cap number is not in any source.
D8. `loading="lazy"` evidence. The lazy-loading data article is partly correlation (pages that lazy-load tend to have worse LCP); only its small A/B test points toward cause. The strongest statements for P5 are the plain instructions in the optimize-LCP and image lazy-loading pages.
D9. CLS definition changed. Older tools sum all shifts for the whole page life; the current definition takes the largest session window (https://web.dev/articles/cls). The Fit check must name which one it uses. The session-window sum is never larger than the all-shifts sum, so using the all-shifts sum would be the stricter check.
D10. Browser coverage. `LayoutShift` (P2) and `PerformanceLongTaskTiming` (P3 proxy) are marked limited availability on MDN (long tasks are also non-standard). They work in Chromium, which is what Playwright launches here, but a Floor that reads them is a Chromium-only measurement. LCP and Event Timing are Baseline in MDN's view (2025).
D11. Google Search page (2026-09-22) says good Core Web Vitals "doesn't guarantee" ranking and that chasing a perfect score for search may "not be the best use of your time". The Prescription should not promise search results from this Floor. It also overlaps the search Floor, which is a separate record.
